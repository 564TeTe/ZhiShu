# 知枢阶段 10.1B：Workspace Provisioner 安全基线说明 v1.0

> 当前状态：阶段 10.1B `COMPLETED`。  
> 阶段 10 总状态：`IN_PROGRESS`。

## 1. 批次边界

本批次实现已批准 Parallel Schedule Lease 的可恢复物理目录分配。默认实现只创建 Control Plane 所有的 marked directory，不调用 Git、不创建分支、不声称已经产生 Git Worktree。

Git-backed Worktree adapter 仍是后续显式能力，必须单独经过权限、路径、命令和清理验收后才能接入。

## 2. 状态机

```text
NOT_STARTED
  -> PROVISIONING
  -> PROVISIONED
  -> CLEANUP_PENDING -> CLEANED
  -> FAILED -> CLEANED
```

逻辑 Lease 状态与 provisioning 状态分离：

- `RESERVED + NOT_STARTED`：已批准、等待 provision；
- `RESERVED + PROVISIONING`：数据库已领取，外部目录动作可能尚未完成；
- `PROVISIONED + PROVISIONED`：目录和 ownership marker 已存在，Assignment 为 `PROVISIONED`；
- `RESERVED + FAILED/CLEANUP_PENDING`：失败或清理重试中，不允许丢失所有权信息；
- `EXPIRED + CLEANED`：TTL 到期且目录已由匹配令牌清理。

## 3. 路径与所有权不变量

1. 路径由 `projectId/scheduleId/workerSlot` 从配置根目录派生，客户端不能提交任意路径。
2. 规范化路径必须严格位于 `zhishu.workspace.provisioning.root` 下，根目录本身不可作为租约目录。
3. provision 创建 `.zhishu-workspace-lease.json` marker，记录 Lease、Schedule、Assignment 和随机 ownership token。
4. cleanup 只有在 marker 存在且 token 完全匹配时才允许删除；缺 marker、令牌不匹配或符号链接都会拒绝。
5. 同一路径只能有一个活动 Lease；数据库唯一索引与 marker 双重保护。
6. Provisioning 失败先持久化失败状态，再尝试补偿清理；清理失败进入 `CLEANUP_PENDING`，由扫描器重试。

## 4. 重启与过期恢复

- 扫描器发现超时 `PROVISIONING` 时，重新读取 marker；marker 匹配则恢复为 `PROVISIONED`，否则按失败补偿。
- `PROVISIONED` 的 `leaseExpiresAt` 到期后清理目录并转为 `EXPIRED/CLEANED`。
- `CLEANUP_PENDING` 在后续扫描中继续尝试，直到 marker 验证通过并完成清理。
- 所有状态变化写入不可变 `workspace_lease_event`；不通过删除数据库记录规避失败。

## 5. API

```text
POST /api/task-center/projects/:projectId/plans/:planId/parallel-schedules/:scheduleId/workspace-leases/:leaseId/provision
```

请求只包含 `clientRequestId`。Gateway 负责认证和稳定 Control Project 解析；Control Plane 负责 Schedule/Assignment/Lease 归属、状态锁定、路径派生和补偿。
