# 知枢阶段 0：现有执行契约基线 v1.0

> 文档性质：阶段 0.2 契约校准结果、阶段 1 数据接入依据。  
> 基线日期：2026-08-15。  
> 适用协议：`control-v1`、`runtime-v1`、Runtime Event Batch `1.0`。  
> 结论：现有执行内核可以复用；本轮只同步契约描述，不改变运行时业务语义。

## 1. 目的与权威来源

本文件回答三个问题：

1. 新任务中心可以读取和复用哪些现有执行事实？
2. OpenAPI / JSON Schema 与真实实现有哪些漂移，如何处理？
3. 阶段 1 可以依赖什么，哪些能力必须继续后置？

发生冲突时，权威顺序为：

1. 当前真实 Controller / Route、DTO / Type、Service 和测试表现。
2. 本文件记录的校准结论。
3. `contracts/control-v1/openapi.yaml`。
4. `contracts/runtime-v1/openapi.yaml` 与 `runtime-events.schema.json`。
5. 旧设计文档或旧 Agent 任务中心前端推断。

说明：本轮审计时，`contracts/`、`control-plane/`、`server/modules/runtime/` 仍属于未跟踪工作树内容。后续不得用清理、重置或整目录覆盖处理这些文件。

## 2. 契约边界

```text
New Task Center（未来）
  → Authenticated Node BFF（未来）
  → Spring Control Plane / control-v1
       → Task / Attempt / Approval / Artifact / Follow-up / Acceptance
       → RuntimeClient
  → Node Runtime / runtime-v1
       → Provider Runtime
       → Runtime Event Outbox
       → Spring Runtime Event Ingestion
```

当前事实所有权：

- Spring Control Plane / PostgreSQL：Task、Attempt、Approval、Artifact、Follow-up、Acceptance、Project/Profile 配置。
- Node Runtime / SQLite + 进程内存：命令幂等、事件 Outbox、当前活动 Run 和待处理 Runtime Approval。
- Provider Runtime：实际 Agent 执行进程与提供商原生会话。
- 新任务中心：阶段 1 只读，不成为任何执行事实的权威来源。

## 3. Control Plane 端点基线

校准后 `control-v1` 共 18 个操作，与 6 个 Spring Controller 的公开映射一致。

| 领域 | 方法与路径 | 真实行为 | 阶段 1 用途 |
|---|---|---|---|
| Project | `POST /api/v1/projects/ensure` | 以候选 UUID 和工作区引用确保 Project 与默认 Profile | 暂不从驾驶台调用 |
| Approval Policy | `GET /api/v1/projects/{projectId}/approval-policy` | 读取项目审批策略 | 只读展示 |
| Approval Policy | `PUT /api/v1/projects/{projectId}/approval-policy` | 替换策略并校验相对目录、命令、超时 | 阶段 1 不调用 |
| Task | `GET /api/v1/tasks` | 可按 `projectId` 过滤；`limit` 被服务端收敛到 1～200 | 总览任务列表 |
| Task | `POST /api/v1/tasks` | 先持久化 Task，再异步启动首个 Attempt；返回 202 | 阶段 1 不调用 |
| Task | `GET /api/v1/tasks/{taskId}` | 当前 Task + 当前 Attempt 快照 | 详情读取 |
| Task | `DELETE /api/v1/tasks/{taskId}` | 当前只允许永久删除终态 Task | 阶段 1 不调用；后续改 Archive |
| Control | `POST /api/v1/tasks/{taskId}/cancel` | 进入 CANCELLING 并发送幂等 Runtime Cancel | 阶段 1 不调用 |
| Control | `POST /api/v1/tasks/{taskId}/retry` | 在同一 Task 下创建新 Attempt | 阶段 1 不调用 |
| Attempt | `GET /api/v1/tasks/{taskId}/attempts` | 返回 Attempt 历史和执行/验收快照 | 执行详情 |
| Follow-up | `GET /api/v1/tasks/{taskId}/follow-ups` | 返回同一 Task 下结构化追问历史 | 执行详情 |
| Follow-up | `POST /api/v1/tasks/{taskId}/follow-ups` | 对当前终态 Attempt 发起幂等追问并创建新 Attempt | 阶段 1 不调用 |
| Acceptance | `POST /api/v1/tasks/{taskId}/acceptance` | 对当前终态 Attempt 记录用户验收决定 | 阶段 1 不调用 |
| Approval | `GET /api/v1/tasks/{taskId}/approvals` | 返回 Task 的待处理审批 | 待处理事项 |
| Artifact | `GET /api/v1/tasks/{taskId}/artifacts` | 返回所有 Attempt 的持久化产物 | 最近证据 |
| Approval | `POST /api/v1/approvals/{approvalId}/decision` | 手工批准/拒绝；Runtime 再执行更严格策略校验 | 阶段 1 不调用 |
| Event | `GET /api/v1/tasks/{taskId}/events` | 支持 `Last-Event-ID` 的单 Task SSE | 第一版可选，轮询优先 |
| Runtime Callback | `POST /internal/control/v1/events:batch` | 鉴权、幂等持久化并投影 Runtime Event Batch | 仅 Node Runtime 调用 |

### 3.1 当前 HTTP 错误模型

Control Plane 的应用错误响应为：

```json
{
  "timestamp": "2026-08-15T00:00:00Z",
  "status": 409,
  "code": "INVALID_TASK_STATE",
  "message": "..."
}
```

当前主要映射：

- `400 INVALID_REQUEST`：Bean Validation、枚举或参数格式错误。
- `404 TASK_NOT_FOUND`：Task、Project/Profile 配置、Approval 或 Policy 不存在。
- `409 INVALID_TASK_STATE`：状态、审批、并发或幂等内容冲突。
- `422 RUNTIME_EVENT_REJECTED`：Runtime Event 身份或关联非法。
- `502 <runtime code>`：Control Plane 调用 Node Runtime 失败，并保留上游错误码。

## 4. Runtime 端点基线

校准后 `runtime-v1` 共 4 个操作，与 `server/modules/runtime/runtime.routes.ts` 一致。统一挂载地址为：

```text
http://127.0.0.1:3001/internal/runtime/v1
```

所有端点都要求：

```http
Authorization: Bearer <ZS_RUNTIME_TOKEN>
```

| 方法与路径 | 真实行为 | 关键限制 |
|---|---|---|
| `GET /health` | 返回无密钥的事件投递/Outbox 健康快照 | Token 未配置为 503；错误 Token 为 401 |
| `POST /runs` | 幂等接受 Start Command，返回 202，异步执行 | 仅 Claude/Codex/OpenCode；OpenCode 正式任务只读 |
| `POST /runs/{runtimeRunId}/cancel` | 中断活动 Provider Run，返回 `aborted` | 依赖进程内活动 Run；重启后可能 404 |
| `POST /runs/{runtimeRunId}/approvals/{runtimeApprovalId}/decision` | 解析待处理权限并再次执行 Runtime 策略 | 非待处理、已终态或策略冲突为 409 |

### 4.1 Runtime 幂等边界

- `requestId`：单次传输请求标识。
- `idempotencyKey`：稳定业务命令键。
- Start、Cancel、Approval Decision 分别记录命令类型、语义 hash 和首次响应。
- 相同 key + 相同语义：返回首次响应，不重复副作用。
- 相同 key + 不同语义：`409 IDEMPOTENCY_CONFLICT`。

### 4.2 Runtime Start 真实限制

- 支持执行器：`claude`、`codex`、`opencode`。
- `cursor` 不属于正式 Agent Task 执行链路。
- OpenCode 当前只接受不含 WRITE_FILE/SHELL/GIT/TEST 的只读任务。
- 非 Claude 执行器不能携带 `connectionRef`。
- `projectRef` 必须存在，且规范化后等于审批策略的 `projectRoot`。
- `allowedDirectories` 必须是项目根目录下的相对路径。
- `trustedCommands` 是精确 argv token 数组，不做前缀匹配。
- 事件投递配置未就绪时，不接受正式 Start。

### 4.3 Runtime 响应

Start：

```json
{ "runtimeRunId": "run_...", "accepted": true }
```

Cancel：

```json
{ "runtimeRunId": "run_...", "aborted": true }
```

Approval Decision：

```json
{
  "runtimeRunId": "run_...",
  "runtimeApprovalId": "...",
  "decision": "APPROVED"
}
```

Runtime 错误响应为：

```json
{
  "code": "IDEMPOTENCY_CONFLICT",
  "message": "...",
  "details": {}
}
```

## 5. Runtime Event Batch 基线

事件信封字段：

- `protocolVersion = 1.0`；
- `eventId`：接收端幂等键；
- `taskId`、`attemptId`：UUID；
- `runtimeRunId`：Node Run 标识；
- `sequenceNo >= 1`：同一 Run 单调递增；
- `occurredAt`：UTC 时间；
- `type`；
- `payload`。

正式事件类型共 10 个：

1. `RUN_STARTED`；
2. `AGENT_STATUS`；
3. `COMMAND_COMPLETED`；
4. `ARTIFACT_PUBLISHED`；
5. `APPROVAL_REQUIRED`；
6. `APPROVAL_RESOLVED`；
7. `ERROR`；
8. `RUN_COMPLETED`；
9. `RUN_FAILED`；
10. `RUN_ABORTED`。

Node 使用 SQLite Outbox 保证事件重试；Spring 负责持久化、去重和状态投影。Token / Thinking 增量不进入该耐久协议。

当前 JSON Schema 对 `ARTIFACT_PUBLISHED` 有结构化 payload；其他 payload 仍是事件类型约定下的对象。阶段 1 读取 Spring 投影，不直接把原始 payload 当成权威 UI DTO。

## 6. Task / Attempt / Approval / Artifact 真实语义

### 6.1 Task

- 表达一个可持续跟进的业务任务。
- `attemptStatus` 是当前执行尝试状态。
- `status` 是兼容别名，当前等于 `attemptStatus`，已标记 deprecated。
- `resolutionStatus` 表达业务解决状态，与执行终态分离。
- Retry 和 Follow-up 都复用同一个 Task ID。

### 6.2 Attempt

- 每次 Start、Retry 或 Follow-up 创建一个新 Attempt。
- Attempt 保存执行器、模型、连接、审批策略、错误和验收快照。
- 历史 Attempt 不被新 Attempt 覆盖。

### 6.3 Approval

- Approval 只针对某个 Attempt 的 Runtime 工具请求。
- Control Plane 保存当次审批策略快照。
- 自动审批与手工审批都必须由 Runtime 再执行更严格的本地策略校验。
- 待审批项可能因取消、超时、终态或并发决定变为不可操作。

### 6.4 Artifact

- 当前类型：SUMMARY、FILE_CHANGE、GIT_DIFF、TEST_REPORT、ERROR_REPORT。
- Artifact 归属 Task + Attempt，是阶段 1 的证据来源。
- Artifact 不是用户验收，也不等于完成事实。

### 6.5 Follow-up

- 只能指向同一 Task 的当前终态 Attempt。
- Task 已 RESOLVED/CLOSED 时不能直接 Follow-up。
- `clientRequestId` 提供幂等；同 key 不同内容为冲突。
- 新 Attempt 获得冻结的 `TASK_FOLLOW_UP_V1` 上下文，包括历史、证据、用户反馈和新验收要求。

### 6.6 Acceptance

- 只能指向当前终态 Attempt。
- `clientRequestId` 提供幂等。
- 决定值：RESOLVED、NEEDS_FOLLOW_UP、CLOSED。
- Acceptance 是人工业务判断，不由 Agent Summary 或 Artifact 自动替代。

### 6.7 Cancel / Retry / Delete

- Cancel：当前 Attempt 进入 CANCELLING，并向 Runtime 发幂等取消命令。
- Retry：仅允许执行终态；创建新 Attempt，不删除历史。
- Delete：当前实现只允许终态 Task，但属于永久删除；阶段 2 必须演进为 Archive + Evidence Protection。

## 7. 本轮发现并同步的契约漂移

| 编号 | 原漂移 | 处理结果 |
|---|---|---|
| C-01 | `control-v1` 缺少 Task List | 已补路径、参数和数组响应 |
| C-02 | `control-v1` 缺少终态 Task Delete | 已补 204/404/409，并明确当前是永久删除 |
| C-03 | 缺少 Project Approval Policy GET/PUT | 已补路径和策略 DTO |
| C-04 | Project Ensure 没有请求/响应 Schema | 已补 EnsureProjectRequest / ProjectRegistration |
| C-05 | Create Task 缺 connection/executor/model/approval 覆盖项 | 已与 Controller DTO 对齐 |
| C-06 | Follow-up 缺执行器和审批覆盖项 | 已与 Controller DTO 对齐 |
| C-07 | Cancel/Retry/Attempt/Follow-up/Acceptance/Approval 缺响应 Schema | 已补真实 DTO |
| C-08 | Approval Decision 缺 path 参数和请求 DTO | 已补齐 |
| C-09 | Control Plane 错误模型不统一可引用 | 已加入复用 ErrorResponse |
| R-01 | Runtime Cancel/Approval Decision 缺响应 Schema | 已补真实响应结构 |
| R-02 | Runtime Start Context 缺 `taskFollowUpContext` | 已补 `TASK_FOLLOW_UP_V1` 结构 |
| R-03 | Runtime OpenAPI 缺真实 400/401/404/409/422/503 | 已按 Route/Service 补齐 |
| E-01 | Event Schema 允许非 UUID taskId/attemptId，但 Java DTO 要求 UUID | 已收紧为 UUID format |

本轮没有：

- 修改协议路径；
- 修改 Controller / Route；
- 修改 Task、Attempt 或 Runtime 状态机；
- 新增数据库迁移；
- 新增执行实体；
- 改变 `protocolVersion: 1.0`。

## 9. 阶段 1 可安全依赖的最小读取面

当前仓库尚不存在受认证的 Node → Control Plane 读取网关。旧 `AgentTaskCenter` 直接从浏览器访问 Control Plane 地址，这种接法不进入新中心；阶段 1 必须建立独立 `server/modules/task-center-gateway/`，浏览器只访问同源 `/api/task-center/**`。

第一版只读驾驶台建议只读取：

1. `GET /api/v1/tasks?projectId=...&limit=...`；
2. `GET /api/v1/tasks/{taskId}`；
3. `GET /api/v1/tasks/{taskId}/attempts`；
4. `GET /api/v1/tasks/{taskId}/approvals`；
5. `GET /api/v1/tasks/{taskId}/artifacts`；
6. `GET /api/v1/tasks/{taskId}/follow-ups`；
7. `GET /api/v1/projects/{projectId}/approval-policy`；
8. `GET /internal/runtime/v1/health`，但必须通过服务端 BFF 使用 Runtime Service Token，浏览器不得持有该 Token。

阶段 1 第一版可轮询。Task SSE 只作为单 Task 详情增强；项目级变化流另行设计，不能伪装成已经存在。
