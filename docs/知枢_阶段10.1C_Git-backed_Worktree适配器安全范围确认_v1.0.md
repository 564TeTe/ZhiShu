# 知枢阶段 10.1C：Git-backed Worktree 适配器安全范围确认 v1.0

> 当前状态：阶段 10.1C `COMPLETED`，安全范围已确认，不实现适配器。  
> 阶段 10 总状态：`IN_PROGRESS`。  
> 本批次不执行 Git 命令、不创建分支、不创建 Work Order、不启动 Agent、不进入 Integration Gate。

## 1. 目的与硬边界

本批次的产物是 Git-backed Worktree adapter 的安全合同和验收清单。它必须独立于已经完成的 `DIRECTORY_ONLY` Provisioner，不能通过替换默认 Bean 或修改现有端点而隐式启用。

在安全范围被明确确认、实现并通过独立验收前：

- `FilesystemWorkspaceProvisioningPort` 继续是唯一默认适配器；
- 现有 Workspace Lease 不得被声称为 Git Worktree；
- 不创建 Work Order、Task、Attempt 或 Agent；
- 不对用户仓库执行任何 Git 命令；
- 不修改主工作区、主分支、远程引用或用户未托管的目录。

## 2. 输入与权威来源

适配器只接受 Control Plane 已确认的结构化输入：

| 输入 | 权威来源 | 约束 |
|---|---|---|
| `projectId` | Project Identity | 仅用于归属校验，不直接拼接用户路径 |
| `scheduleId` / `leaseId` | 已批准 Parallel Schedule Lease | 必须处于可 provision 状态，并与 Project、Plan 归属一致 |
| 仓库根路径 | 已确认 Workspace Binding | 由服务端解析并 canonicalize，客户端不得提交替代路径 |
| 基线提交 | 受控 Plan/Proposal 版本 | 必须解析为完整、稳定的提交对象，禁止把未验证文本直接传给命令 |
| worker slot | Assignment | 由服务端分配，用于确定性命名和并发隔离 |

适配器不得接受任意 shell 字符串、任意环境变量、任意工作目录、任意分支名或任意 cleanup 路径。

## 3. 命令执行白名单

实现时必须使用 `ProcessBuilder` 的参数数组或等价的无 shell API；禁止 `cmd.exe /c`、PowerShell、bash、字符串拼接命令和用户可控的 PATH 覆盖。

首版只允许以下逻辑操作，具体 argv 需在实现批次中固定并测试：

1. 读取并验证仓库根：`rev-parse --show-toplevel`；
2. 创建受控 worktree：`worktree add`，目标路径和基线提交均由服务端解析；
3. 验证 worktree 归属：`worktree list --porcelain`；
4. 清理本 Lease 创建的 worktree：`worktree remove`，仅允许匹配 ownership marker 的目标路径；
5. 清理本 Lease 创建且确认未推送的临时分支（若最终方案选择分支模式）。

以下操作明确禁止：`push`、`fetch`、`pull`、`reset --hard`、`clean -fdx`、修改远程配置、修改 hooks、修改主工作区索引、任意 `-c` 配置注入，以及把未审计参数透传给 Git。

命令执行必须记录 operation id、固定 argv 摘要、退出码、耗时和 stdout/stderr 摘要；不得把 ownership token、服务凭据或完整仓库内容写入审计日志。

## 4. 仓库根路径与主工作区隔离

- 解析后的仓库根必须是已绑定 Workspace 的真实目录，并且在允许的项目根范围内；符号链接、junction、越界路径和不存在的路径均拒绝。
- Worktree 目标目录必须由 `projectId/scheduleId/workerSlot/leaseId` 派生，位于独立 provisioning 根下；客户端不能指定目标路径。
- 目标目录不得等于仓库根、主 worktree、任何现有 worktree 或其父目录；创建前后都要用 canonical path 和 `worktree list --porcelain` 双重校验。
- 一个活动 Lease 只能拥有一个目标路径；同一路径、同一分支和同一 ownership token 必须由数据库唯一约束保护。
- 主工作区发生任何变化时，适配器必须停止后续操作并留下失败审计，不得自动恢复、重置或覆盖主工作区。

## 5. 分支命名与基线

若最终采用分支模式，分支名必须由服务端从稳定 ID 派生，例如 `zhishu/ws/<schedule-short>/<slot>-<lease-short>`；不得使用用户输入、空白、路径遍历片段或可改变语义的 Unicode 变体。

分支创建必须：

- 绑定已确认的完整基线提交；
- 在数据库中先记录预期分支名、基线对象和 ownership token；
- 创建后立即通过 `worktree list --porcelain` 和对象解析结果复核；
- 不自动推送、不改变默认分支、不复用已存在的非本 Lease 分支。

若分支已存在但 ownership marker 不匹配，操作必须失败并进入补偿流程；不得强制接管。

## 6. 失败回滚与清理

失败处理必须保持与 V19 Provisioner 相同的可恢复语义：数据库先进入 `PROVISIONING`，外部动作完成后才进入 `PROVISIONED`；任何中断都由扫描器恢复或补偿。

- 创建命令失败：保留失败原因和退出码，只有在 marker、目标路径和 ownership token 全部匹配时才允许清理。
- 创建成功但数据库提交失败：重启扫描器必须能够通过 marker 和 worktree 元数据恢复；不能重复创建或删除未知目录。
- 清理失败：进入 `CLEANUP_PENDING`，按退避策略重试；不使用 `reset --hard` 或 `clean -fdx` 作为兜底。
- 发现路径、分支或 worktree 元数据不匹配：拒绝清理并保持人工介入所需证据，不能扩大删除范围。
- Lease TTL 到期：先阻止后续派发，再执行受 ownership 保护的 worktree/分支清理；清理完成后才标记 `EXPIRED/CLEANED`。

## 7. 审计证据与验收门槛

至少需要以下不可变事件：`WORKTREE_VALIDATION_STARTED`、`WORKTREE_CREATED`、`WORKTREE_CREATE_FAILED`、`WORKTREE_CLEANUP_STARTED`、`WORKTREE_CLEANED`、`WORKTREE_CLEANUP_FAILED`、`WORKTREE_RECOVERED`。每个事件必须带 Lease、Schedule、Assignment、actor/system actor、operation id、目标路径摘要、基线对象和结果摘要。

实现批次通过前必须完成：

- 临时测试仓库中的创建、幂等重放、进程中断恢复、TTL 清理和失败补偿；
- 越界路径、符号链接、主工作区、错误 token、错误分支和已存在非归属 worktree 的拒绝测试；
- 命令白名单测试，证明没有 shell、远程写入或主工作区修改；
- Control Plane、Gateway、OpenAPI、双端构建和真实 Demo 验证；
- 证据确认：未创建 Work Order、未启动 Agent、未触碰用户仓库之外的目录。

## 8. 当前结论

本文件只冻结安全范围，不代表 Git-backed Worktree adapter 已实现或可用。用户已于 2026-08-15 通过“继续”确认上述边界；在“不处理 Git”的既有约束下，Git-backed 实现批次仍保持未启动。默认 `DIRECTORY_ONLY` Provisioner 的行为和接口保持不变，API 通过 `physicalWorkspaceKind=DIRECTORY_ONLY` 明确暴露当前物理事实。
