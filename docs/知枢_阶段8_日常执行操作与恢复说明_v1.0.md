# 知枢阶段 8：日常执行操作与恢复说明 v1.0

> 适用批次：阶段 8.1～8.4 日常闭环、历史、恢复、指标与默认入口。  
> 当前状态：阶段 8.1～8.4 已完成，G8 最终 Gate 为 `PASSED`。  
> 默认入口：默认启用一次性 `task-center` 迁移；Legacy Tab 继续独立保留。

## 1. 新中心已覆盖的日常操作

Task Center 的执行详情现在可以直接处理：

- 当前活动 Attempt 的取消；
- FAILED、ABORTED 的新 Attempt 重试；
- LOST 的专用恢复，新建 Attempt，不复活旧 Runtime Run；
- 当前终态 Attempt 的 Follow-up；
- 当前终态 Attempt 的业务验收：RESOLVED、NEEDS_FOLLOW_UP、CLOSED；
- 当前 PENDING Approval 的批准或拒绝；
- Artifact、Attempt、Follow-up、Acceptance 和 Work Order 历史读取。

Work Order 验证继续使用阶段 7 的 Verification Gate。业务 Acceptance 不替代 Work Order 的 System Evidence 和 Human Verification。

## 2. 身份与调用边界

浏览器只调用受用户 JWT 保护的同源 `/api/task-center/**`。Gateway 从认证会话生成 `user:<id>` actor，并通过 `X-Zhishu-Actor` 传给受 Service Credential 保护的 Project Control 内部命令。

每个 Task 命令在转发前都会重新解析稳定 Control Project，并读取 Task 归属。猜测其他项目的 Task ID 或 Approval ID 不会越过项目边界。

Follow-up 和 Acceptance 的 actor 不接受浏览器自报；服务端使用认证 actor。Approval 的人工决定也保存该 actor，而不是统一记录为匿名 `user`。

## 3. 状态前置条件

| 操作 | 前置条件 | 结果 |
|---|---|---|
| Cancel | 当前 Attempt 非终态 | 进入 CANCELLING；历史保留 |
| Retry | 当前 Attempt 为 FAILED、LOST 或 ABORTED | 创建新 Attempt；原 Attempt 保持终态 |
| LOST Recovery | 当前 Runtime Health 为 LOST | 创建新 Attempt；旧 Run 迟到事件保持隔离 |
| Follow-up | 当前 Attempt 已终态，Task 未 RESOLVED/CLOSED | 创建结构化 Follow-up 和新 Attempt |
| Acceptance | 指向当前终态 Attempt | 记录人工业务决定和原因 |
| Approval Decision | Approval 仍为当前 Task 的 PENDING 项 | 继续复用 Runtime 审批策略与并发保护 |

Retry 若关联阶段 7 Work Order，仍受 Work Order 当前性、失败状态和 Verification 结果约束。已 VERIFIED、REJECTED 或历史 superseded Work Order 不会被新入口绕过。

## 4. 幂等与恢复

- Follow-up 与 Acceptance 由浏览器生成稳定单次 `clientRequestId`，相同请求重放返回原结果；相同 key 不同内容仍冲突。
- Approval Decision 继续使用 Approval ID 派生 Runtime 幂等键。
- Cancel、Retry 和 LOST Recovery 继续复用既有 Task Control 与 Runtime 命令幂等。
- 页面命令成功后立即刷新当前详情和 Dashboard；失败时保留当前服务端快照并显示错误，不伪装操作成功。
- 页面刷新或 Gateway 重启不会丢失已提交结果，所有历史从 Control Plane 重新读取。

## 6. 回退

- `VITE_ZHISHU_TASK_CENTER_ENABLED=false` 仍可隐藏新中心入口，不删除 Task、Attempt、Approval、Artifact、Acceptance、Follow-up、Work Order 或 Project State 数据。
- `VITE_ZHISHU_TASK_CENTER_PRIMARY=false` 停止新的默认页签迁移并保留 Chat 默认，不隐藏新中心，也不修改任何服务端数据。
- 一次性迁移标记为 `zhishu.task-center.primary-rollout=1`；已处理迁移后，用户后续选择 Chat、Legacy 或其他有效 Tab 都不会再被覆盖。
- Legacy AgentTaskCenter 保持独立，既不作为新中心的数据迁移工具，也不影响新中心服务端历史。
- 阶段 8.4 没有数据库迁移；回退前端入口无需清理服务端数据。
