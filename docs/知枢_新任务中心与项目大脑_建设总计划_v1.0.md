### 0.1 项目最终目标

在不重写现有 Agent 执行链路的前提下，新建一个面向长期软件项目推进的任务中心：

```text
用户
  ↕
New Task Center
  ├─ Project Brain
  ├─ Project State
  ├─ Plan Center
  ├─ Execution Dashboard
  └─ Evidence / Decision
          ↓
Existing Execution Kernel
Task / Attempt / Approval / Artifact / Runtime
```

新中心是项目级控制面，不是旧 `AgentTaskCenter` 的重构版，也不是第二套执行系统。

# 2. 正式建设方向

## 2.1 一句话结论

> 新任务中心复用现有执行能力及其服务端行为契约，而不是复用旧 `AgentTaskCenter` 的前端实现；它在现有执行内核之上新增项目身份、项目状态、项目大脑、版本化计划、工作单和证据回流。

## 2.2 产品定位

旧中心回答：

- 一个 Task 的 Attempt 如何执行；
- 使用了哪个执行器；
- 调用了什么工具；
- 为什么等待审批；
- 哪一步失败；
- 产生了什么 Artifact；
- 是否 Retry、Follow-up 或 Cancel。

新中心回答：

- 当前项目的目标和阶段是什么；
- 已确认哪些决策与约束；
- 当前计划是什么，为什么这样安排；
- 做到哪一步，哪些节点阻塞；
- 哪些工作正在执行；
- 执行结果有哪些可信证据；
- 哪些只是 AI 建议；
- 哪些事项需要用户决定；
- 下一步应该做什么。

## 2.3 核心架构原则

1. 新增上层，复用下层。
2. Project Identity 不等于 Workspace Path。
3. Project State 是权威项目语义状态，Brain 不是事实数据库。
4. 所有 LLM 行为遵循 Proposal First。
5. Plan Version 表达计划结构变化，执行进度单独保存。
6. Plan Node 不等于 Task，二者通过 Work Order 连接。
7. Agent Claim、System Evidence、Human Verification 必须分层。
8. 证据默认保留，业务删除优先变成 Archive。
9. 所有跨层命令必须考虑幂等、版本和并发。
10. Brain、Planner、State Steward 按事件启动，不常驻互聊。
11. 普通 Chat 不作为本次建设前提。
12. 多 Agent、Worktree 和 Integration Gate 后置。

# 6. 数据所有权、认证与服务边界

## 6.1 数据所有权

### Spring Control Plane / PostgreSQL 所有

- Project Identity。
- Workspace Binding 元数据。
- Project State 和 Revision。
- Decision / Constraint / Discovery / Risk。
- Brain Thread / Brain Run / Proposal 审计元数据。
- Plan / Plan Version / Plan Node / Plan Execution State。
- Work Order / Execution Binding。
- Task / Attempt / Approval / Acceptance / Follow-up。
- Execution Report / Verification / Evidence Reference。
- Project Change Log。

### Node / SQLite 所有

- Provider 连接与本机密钥。
- Runtime Command Dedup。
- Runtime Event Outbox。
- 活动 Provider Run 的进程态数据。
- 现有普通 Chat 和本地执行基础设施。

### 原则

- Node 不直接查询 PostgreSQL。
- Spring 不直接查询 Node SQLite。
- 二者通过版本化内部协议、稳定 ID 和服务令牌协作。
- 前端不承担项目事实源职责。

## 6.2 推荐的新中心访问路径

V1 推荐使用 Node 作为新中心的受认证 BFF：

```text
Browser
  │ User JWT
  ▼
Node Task Center Gateway
  │ Service Credential
  ▼
Spring Control Plane
```

Brain 推理路径：

```text
Browser
  → Node Task Center Gateway
  → Spring 创建 Brain Run / 生成 Context Package
  → Node Project Intelligence 调用模型
  → 流式返回 Browser
  → Proposal / 消息 / Run 结果回写 Spring
```

Node 只是网关和模型执行位置，不成为权威项目状态所有者。

## 6.3 两类信任边界

### User/Auth Boundary

至少区分：

- 查看项目；
- 修改 State；
- 确认 Decision；
- 批准 Plan；
- 分发 Work Order；
- 验收执行结果。

V1 可以只有一个本地用户，不必立即实现复杂 RBAC，但所有写操作必须记录 actor。

### Runtime Trust Boundary

继续使用独立服务令牌保护：

- Spring → Node Start / Cancel / Approval Decision；
- Node → Spring Runtime Event；
- 新增的 Brain/Planner 内部运行协议。

用户令牌不能替代 Runtime 服务令牌，Runtime 服务令牌也不能冒充用户决策。

# 7. 核心领域模型规划

本节定义语义，不强制最终类名或表名。实现前仍需结合代码审计确认命名。

## 7.1 Project Identity 与 Workspace Binding

### Project

代表长期项目身份，核心字段概念：

- `projectId`：稳定内部主键；
- `displayName`；
- `repositoryIdentity`：规范化仓库来源，可为空；
- `status`：ACTIVE / ARCHIVED；
- `createdAt / updatedAt`。

### Workspace Binding

代表项目在某台机器上的当前挂载：

- `workspaceId`；
- `projectId`；
- `machineId`；
- `workspacePath`；
- `repositoryUrl / remoteFingerprint`；
- `branch`；
- `isPrimary`；
- `lastSeenAt`；
- `status`。

### 身份规则

- 路径变化不自动创建新 Project。
- 同一 Project 可以有多个 Workspace Binding。
- 首次识别无法确定时创建 Identity Proposal，必要时让用户确认。
- V1 仍可单机运行，但数据模型不把路径当永久身份。

## 7.2 Project State

### Project Snapshot

用于快速读取当前状态：

- 当前 Goal；
- 当前 Stage；
- 当前状态摘要；
- 当前 Blocker；
- 关键 Decision / Constraint 摘要；
- 当前 Plan 引用；
- `stateRevision`；
- `updatedAt`。

Snapshot 是可重建的当前读模型，不取代来源记录。

### State Entry 分类

- FACT：可验证事实；
- DECISION：已确认决策；
- CONSTRAINT：对计划和执行有效的约束；
- DISCOVERY：执行或分析发现；
- RISK：已识别风险；
- ASSUMPTION：推理假设，不进入权威状态；
- GOAL：项目目标；
- STAGE：项目阶段。

### 权威等级

从高到低：

```text
SYSTEM_VERIFIED
USER_CONFIRMED
AGENT_OBSERVED
AGENT_INFERRED
```

规则：

- 测试真实退出码、Task 状态和 Artifact 存在性可形成 SYSTEM_VERIFIED Fact。
- 用户明确确认的方向形成 USER_CONFIRMED Decision/Constraint。
- Agent 发现架构问题通常是 AGENT_OBSERVED Discovery。
- Agent 推测只能是 AGENT_INFERRED Assumption/Proposal。

### Provenance

每个可追溯状态项至少记录：

- `sourceType`；
- `sourceId`；
- `authorityLevel`；
- `createdBy`；
- `observedAt / confirmedAt`；
- Evidence Reference；
- `status`：ACTIVE / SUPERSEDED / STALE / DISMISSED；
- 可选 `supersedesId`。

## 7.3 State Revision 与 Project Change Log

### stateRevision

只在项目语义状态发生变化时增加，例如：

- Goal、Stage 变化；
- Decision 或 Constraint 生效；
- 重要 Fact 形成或失效；
- Discovery 被确认或驳回；
- 关键风险状态变化。

以下内容不直接增加 `stateRevision`：

- Token 增长；
- 普通工具事件；
- Heartbeat；
- 页面刷新；
- Artifact 被下载；
- 普通执行日志。

### Project Change Log

V1 使用事件思想而非完整 Event Sourcing：

- 保存发生了什么；
- 保存来源、actor、时间和前后 revision；
- 维护当前 Snapshot；
- 不要求所有数据库状态都由事件回放重建。

## 7.4 Composite Context Version

每个 Context Package 至少带：

```text
stateRevision
planVersion
executionWatermark
contextGeneratedAt
contextPackageVersion
```

含义：

- `stateRevision`：慢变化的项目语义状态；
- `planVersion`：当前正式计划结构版本；
- `executionWatermark`：本次读取执行数据的位置；
- `contextGeneratedAt`：上下文生成时间；
- `contextPackageVersion`：上下文结构协议版本。

## 7.5 Context Package V1

### BrainContextPackageV1

包含：

- Project Identity 与当前 Workspace；
- Goal / Stage / State Revision；
- Active Plan 摘要；
- 关键 Decisions / Constraints；
- 当前 Blockers / Risks；
- 最近重要 Changes；
- 相关 Execution Report / Evidence 摘要；
- 本轮用户问题；
- 版本和截断信息。

### PlannerContextPackageV1

包含：

- 用户目标；
- 当前 Project State；
- 当前 Plan Definition；
- 未完成节点和依赖；
- Constraints；
- Worker Capability Matrix；
- 最近失败、阻塞和 Replan 原因；
- 基础版本。

### WorkOrderContextPackageV1

只包含执行这一项工作所需内容：

- Objective；
- Scope；
- Acceptance Criteria；
- Relevant Files / Modules；
- Constraints；
- Dependencies；
- Base Revision；
- Expected Evidence；
- Expected Report Version。

## 7.6 Proposal First

所有 LLM 影响权威状态的行为必须经过：

```text
LLM Output
  ↓
Typed Proposal
  ↓
Schema Validation
  ↓
Conflict / Permission Validation
  ↓
User Approval 或确定性 Auto Rule
  ↓
Authoritative State
```

Proposal 类型至少包括：

- StateChangeProposalV1；
- DecisionProposalV1；
- PlanProposalV1；
- PlanPatchProposalV1；
- WorkOrderProposalV1；
- DiscoveryProposalV1。

Proposal 通用状态：

```text
DRAFT
PENDING_VALIDATION
PENDING_APPROVAL
APPROVED
REJECTED
STALE
APPLIED
FAILED
```

每个 Proposal 记录：

- schema/version；
- source Brain/Planner/Steward Run；
- base context version；
- payload；
- validation result；
- actor 与审批记录；
- applied revision/version；
- 幂等请求 ID。

## 7.7 Project Brain

### Brain Thread

保存项目协作对话，不等于 Project State：

- `threadId`；
- `projectId`；
- 标题和状态；
- 创建者；
- 创建/更新时间。

### Brain Message

- 用户或 Brain 消息；
- 关联 Brain Run；
- 关联 Context Package 版本；
- 可选 Proposal 引用；
- 不自动成为 Decision。

### Brain Run

- `roleVersion`；
- `model / provider`；
- `promptVersion`；
- `contextPackageVersion`；
- Composite Context Version；
- Token / 时间 / 状态；
- 输出和错误；
- 产生的 Proposal。

## 7.8 Plan Center

### Plan

代表一个项目推进目标，保存当前正式版本引用。

### Plan Version

表示计划结构的一次正式版本：

- 版本号；
- 目标；
- 创建原因；
- base state revision；
- 来源 Proposal；
- 审批人和发布时间；
- 前一版本引用；
- 发布后不可变。

### Plan Node Definition

属于某个 Plan Version：

- 稳定逻辑 `nodeKey`；
- 标题、目标、范围；
- Acceptance Criteria；
- 优先级；
- 推荐 Worker 能力；
- 是否需要人工审批；
- 依赖；
- 来源与继承关系。

### Plan Node Version Relation

Replan 时节点关系：

- INHERITED；
- SUPERSEDED；
- CANCELLED；
- NEW。

### Plan Execution State

与 Plan Version 分开，允许频繁更新：

```text
NOT_READY
READY
APPROVED_FOR_EXECUTION
DISPATCHING
RUNNING
WAITING_APPROVAL
VERIFYING
BLOCKED
COMPLETED
FAILED
CANCELLED
SUPERSEDED
```

Task 运行状态变化只更新 Plan Execution State，不生成新 Plan Version。

## 7.9 Work Order 与 Execution Binding

### Work Order V1

Plan Node 被批准执行后生成：

- `workOrderId`：稳定幂等身份；
- `projectId / planId / planVersion / nodeKey`；
- Objective；
- Scope；
- Acceptance Criteria；
- Constraints；
- Base Context Version；
- 推荐/选定 Executor；
- Permission Policy；
- Expected Evidence；
- Expected Report Version；
- 状态与创建者。

### Work Order 生命周期

```text
DRAFT
READY
DISPATCHING
DISPATCHED
RUNNING
VERIFYING
COMPLETED
BLOCKED
FAILED
CANCELLED
```

### Execution Binding

记录：

- `workOrderId`；
- `taskId`；
- 当前/历史 `attemptId`；
- 绑定时间；
- 绑定幂等键；
- 状态同步信息。

幂等规则：同一 `workOrderId` 重复分发必须返回原绑定，不创建第二个 Task。

## 7.10 Execution Report V1

自然语言 Summary 继续保留，但不能替代结构化报告。

### A. Agent Claims

- Agent 声称完成了什么；
- Agent 声称修改了哪些内容；
- Agent 解释的根因；
- Agent 建议的下一步。

默认权威等级较低。

### B. System Evidence

- Attempt 终态；
- Runtime exit code；
- Tool/command 结果；
- 实际 changed files；
- Git Diff Artifact；
- Test / Build / Lint 命令和退出结果；
- Artifact ID 与 hash；
- Approval 与拒绝记录。

### C. Human Verification

- 用户验收结果；
- 验收说明；
- 是否要求 Follow-up；
- 验收 actor 和时间。

### ExecutionReportV1 结果

- result：SUCCESS / PARTIAL / BLOCKED / FAILED；
- summary；
- changes；
- verification；
- discoveries；
- risks；
- blockers；
- suggestedNextActions；
- evidenceRefs；
- claim/evidence/verification 分层；
- reportVersion。

## 7.11 Verification Gate

Plan Node 不能因为 Agent 返回成功就直接 COMPLETED。

推荐映射：

```text
Attempt SUCCEEDED
  → Work Order VERIFYING
  → 系统证据检查
  → 必要时用户 Acceptance
  → Plan Node COMPLETED
```

失败分类：

- Execution Failure：Retry / Follow-up / 新 Attempt；
- Verification Failure：补测试、补证据或用户拒绝；
- Plan Failure：BLOCKED → Replan Proposal。

## 7.12 Evidence Retention 与 Archive

默认行为：

- Task、Attempt、Artifact、Report 被 Project State、Decision、Plan 或 Work Order 引用后，不允许物理级联删除；
- 用户“删除”优先变为 Archive；
- 归档内容不出现在默认活动视图，但仍可追溯；
- 真正物理删除需要引用检查、显式高风险确认和审计；
- Artifact 大文件存储、下载和保留策略后置，但引用语义从 V1 建立。

# 8. 智能角色与安全合同

## 8.1 Role Contract 必须版本化

首版角色标识建议：

```text
project-brain:v1
project-planner:v1
state-steward:v1
```

每次运行记录：

- roleVersion；
- promptVersion；
- model/provider；
- contextPackageVersion；
- outputSchemaVersion；
- 权限清单。

Role Contract V1 推荐由代码和版本化配置管理，运行时保存版本和必要快照；不要把认知角色硬塞进现有 Worker `agent_profile`。

## 8.2 Project Brain

可以：

- 读取 Context Package；
- 查询当前 State、Plan、Execution Report 和 Evidence；
- 解释项目；
- 给出建议；
- 生成 Proposal；
- 请求 Planner；
- 请求用户确认。

不可以：

- Shell、Git、文件写入；
- 直接修改 State；
- 直接发布 Plan Version；
- 直接分发大规模 Work Order；
- 把聊天记忆覆盖服务端状态。

## 8.3 Planner

可以：

- 读取 Planner Context Package；
- 拆解节点和依赖；
- 建议并行；
- 生成 Plan Proposal / Plan Patch Proposal；
- 为节点准备 Work Order Proposal。

不可以：

- 写代码；
- 直接改变项目事实；
- 直接发布计划；
- 自己宣布节点完成。

## 8.4 State Steward

可以：

- 从报告提取 Discovery 候选；
- 标记冲突和 stale；
- 合并重复候选；
- 生成 State Change Proposal。

不可以：

- 无证据生成 Fact；
- 替用户做 Decision；
- 删除历史；
- 直接改变 Plan。

## 8.5 Worker

继续使用 Existing Execution Kernel：

- 获取最小 Work Order Context；
- 阅读相关代码；
- 在权限范围内修改和验证；
- 产生 Agent Claim 和 Runtime Evidence；
- 不决定项目战略；
- 不自动扩张下一批任务。

## 8.6 Prompt Injection 边界

```text
External Content
  → Worker
  → Agent Claim / Runtime Evidence
  → Validation
  → Proposal
  → User / Rule
  → Project State
```

仓库文件、日志和网页中的文字不能直接成为用户 Decision。

# 9. API、协议与模块边界规划

## 9.1 契约策略

- 保持现有 `control-v1` 和 `runtime-v1` 执行契约兼容。
- 阶段 0 先补齐现有 OpenAPI 与真实 Controller 的漂移。
- 新项目控制能力建议建立独立 `project-control-v1` 契约。
- Brain/Planner 内部执行建议建立 `project-intelligence-v1` 契约。
- `ContextPackageV1`、`WorkOrderV1`、`ExecutionReportV1` 单独有 JSON Schema。
- 不为了加字段随意改变旧语义；不兼容变化必须显式升版。

## 9.2 新中心 BFF 概念接口

前端只调用同源受认证接口，例如：

```text
/api/task-center/projects/:projectId/dashboard
/api/task-center/projects/:projectId/state
/api/task-center/projects/:projectId/changes
/api/task-center/projects/:projectId/brain/threads
/api/task-center/projects/:projectId/brain/runs
/api/task-center/projects/:projectId/plans
/api/task-center/work-orders/:workOrderId/dispatch
```

实际路径在实现前结合现有路由规范确认。

## 9.3 Spring 项目控制接口能力

至少支持：

- Project Identity / Workspace ensure、link、move；
- Dashboard Aggregate Read Model；
- State Snapshot 和 Entry 查询；
- Proposal 创建、验证、批准、拒绝；
- Decision / Constraint 生命周期；
- Context Package 生成；
- Brain Thread / Run 审计记录；
- Plan Proposal、发布和版本查询；
- Plan Execution State；
- Work Order 创建与幂等分发；
- Execution Report / Verification；
- Project Change SSE。

## 9.4 Node 模块边界

按仓库后端规范，新 Node 能力应建立独立 feature module 和 `index.ts` 公共出口，避免继续扩张现有 `runtime.service.ts`。

建议概念模块：

```text
server/modules/task-center-gateway/
server/modules/project-intelligence/
```

- Gateway 负责用户认证后的转发、输入校验和流式桥接。
- Project Intelligence 负责无代码工具权限的 Brain/Planner 模型运行。
- Existing Runtime 继续只负责 Worker 执行。
- 跨模块只能通过 barrel 公共 API。

## 9.5 前端模块边界

建议新建：

```text
src/components/task-center/
  api/
  hooks/
  model/
  view/
  view/subcomponents/
```

要求：

- 不导入 `components/agent-tasks/**`；
- 不把全部状态和 JSX 再写进一个巨大组件；
- API DTO、领域视图模型和 UI 状态分离；
- 页面级订阅与查询集中管理；
- 可以复用 `agent-tasks` 之外的通用 Button、Dialog、Markdown、Editor、主题和 HTTP 基础设施。

# 11. 关键业务流程

## 11.1 Project Bootstrap

```text
选择本地 Workspace
  → 识别 Git / Existing Project Mapping
  → 找到或创建 Project Identity Proposal
  → 绑定 Workspace
  → 读取现有 Task / Attempt / Artifact
  → 生成 Initial State Proposal
  → 用户确认
  → Project State Revision 1
```

第一次不全量理解整个代码库，只建立足够推进下一步的状态。

## 11.2 Brain 问答

```text
用户问题
  → 创建 Brain Run
  → Context Builder 生成 BrainContextPackageV1
  → Node Project Intelligence 运行无写权限模型
  → 流式回复
  → 保存消息与运行元数据
  → 如需改变权威状态，仅生成 Proposal
```

## 11.3 计划生成与批准

```text
用户目标 / Brain 建议
  → PlannerContextPackageV1
  → Planner Run
  → PlanProposalV1
  → Schema / Revision / Dependency Validation
  → 用户讨论、修改、部分批准或拒绝
  → 发布不可变 Plan Version
```

## 11.4 Plan Node 到执行

```text
Plan Node READY
  → 用户/规则批准执行
  → WorkOrderV1
  → 幂等认领 workOrderId
  → Existing Task + Attempt
  → Execution Binding
  → Worker 执行
```

## 11.5 执行回流

```text
Runtime Events / Artifacts
  → Attempt 终态
  → ExecutionReportV1 聚合
  → Verification Gate
  ├─ 通过 → Node COMPLETED
  ├─ 需用户验收 → VERIFYING
  ├─ 执行失败 → Retry / Follow-up
  └─ 计划失败 → BLOCKED / Replan Proposal
  → State Reducer
  → Semantic Project Change
  → 新 Context Package
  → Brain 总结下一步
```

## 11.6 Replan

```text
Node BLOCKED / 用户改变目标 / Constraint 变化
  → PlanPatchProposalV1
  → 对比当前 Plan Version 和 State Revision
  → 标记继承/替换/取消/新增节点
  → 用户批准
  → 发布 Plan Version N+1
```

## 11.7 Runtime 失联

```text
RUNNING
  → Heartbeat 暂时缺失
  → UNKNOWN
  → Lease 过期且 Run 无法恢复
  → LOST
  → 用户选择重新执行
  → 新 Attempt
```

LOST 不能伪装成 FAILED，也不能自动复活旧 Attempt。

# 12. 分阶段实施总计划

整个建设分为四个大周期、十个阶段。每个阶段必须独立可验证和可回退。

## 第一大周期：新壳子

### 阶段 0：基线固化与新中心隔离

#### 目标

建立不依赖旧前端的新功能边界，并确认当前执行内核的真实契约。

#### 工作项

1. 检查 Git 状态并记录用户已有修改。
2. 读取 `AGENTS.md` 和后端模块规范。
3. 运行或记录当前可行的基线 typecheck、相关测试和构建结果。
4. 校准现有 Control Plane OpenAPI 与真实 Controller。
5. 校准 Runtime OpenAPI / JSON Schema 与真实类型。
6. 明确现有 Task/Attempt/Approval/Artifact/Follow-up/Acceptance 契约。
7. 新增独立 `task-center` Tab 类型和空壳模块。
8. 保证新模块不导入 `components/agent-tasks/**`。
9. 定义新中心 feature flag 或可移除入口。
10. 在本文更新实际基线和下一步。

#### 交付物

- 可打开的新 Task Center 空壳。
- 契约差异清单和已同步契约。
- 新旧前端依赖检查结果。
- 基线验证记录。

#### 验收

- 移除新 Tab 后，共享执行内核不受影响。
- 新中心代码中不存在对旧 Agent Task Center 的业务导入。
- 不新增第二套执行实体。
- 旧执行 API 没有被无版本地改变。

#### 不做

- 不做 Brain、State、Plan。
- 不重构旧页面。
- 不改变 Task 创建语义。

### 阶段 1：只读项目驾驶台

#### 目标

用新产品结构读取现有执行事实，证明新中心可独立存在。

#### 工作项

1. 建立新中心 API Client / Gateway。
2. 提供项目执行聚合查询：
   - 活动任务；
   - 等待审批；
   - 最近成功、失败、取消；
   - Attempt；
   - Artifact；
   - Acceptance / Follow-up；
   - Control Plane / Runtime Health。
3. 实现总览和执行只读视图。
4. 第一版可以轮询；同时设计项目级变化订阅。
5. 清晰显示数据来源和健康状态。

#### 验收

- 用户不打开旧中心，也能知道当前有哪些执行、是否等待操作、最近结果是什么。
- 所有展示数据来自现有服务端事实。
- 页面没有创建 Task、改 State、改 Plan 的入口。
- Runtime 不健康时明确提示，不能假装数据正常。

#### 不做

- 不做执行写操作。
- 不做长期 State。
- 不让 AI 生成项目总结。

## 第二大周期：项目智能

### 阶段 2：Project Identity、认证与证据保护

#### 目标

在长期状态落库前解决身份、安全和证据生命周期问题。

#### 工作项

1. 设计 Project / Workspace Binding 迁移。
2. 建立现有路径项目的兼容映射。
3. 设计项目移动、重新绑定和歧义确认流程。
4. 新中心接入 User/Auth Boundary。
5. 建立 Node BFF → Spring 的 Service Credential。
6. 分离用户身份和 Runtime 服务身份。
7. 为写操作记录 actor。
8. 把 Task 业务删除逐步改为 Archive。
9. 建立 Evidence Reference 和引用保护。
10. 保持现有执行协议兼容。

#### 验收

- 移动 Workspace 后可以重新绑定到同一 Project。
- 未认证用户不能访问新中心业务数据。
- Runtime Token 不能冒充用户批准计划或决策。
- 被 Decision/Plan/Report 引用的 Evidence 不会被普通删除破坏。

#### Gate

未通过本阶段，不进入可写 Project State。

### 阶段 3：Project State V1 与 Context Builder

#### 目标

建立可信、可追溯、可版本化的项目语义状态。

#### 工作项

1. 建立 Project Snapshot 和 `stateRevision`。
2. 建立 Goal、Stage、Fact、Decision、Constraint、Discovery、Risk。
3. 建立 authority level、provenance、evidence refs 和 supersedes。
4. 建立 Project Change Log 和 Reducer。
5. 从现有 Task/Attempt/Artifact 派生低风险系统 Fact。
6. 建立 Initial State Proposal 和用户确认流程。
7. 建立 Composite Context Version。
8. 建立 BrainContextPackageV1 / PlannerContextPackageV1 基础。
9. 建立项目级变化 SSE 或等价订阅。
10. 新中心增加状态/决策只读与确认视图。

#### 验收

- 用户不读历史聊天即可知道当前目标、阶段、阻塞和关键约束。
- 每个正式 Decision 可以说明谁确认、为什么和证据在哪里。
- 普通 Runtime 日志不会不停增加 `stateRevision`。
- 同一个 State Change 重放不会重复应用。
- 旧版本 Context Package 仍可解释。

### 阶段 4：Project Brain 只读协作

#### 目标

让用户第一次可以与基于真实项目状态的 Brain 协作。

#### 工作项

1. 建立 Brain Thread / Message / Run。
2. 建立 `project-brain:v1` Role Contract。
3. 建立无 Shell、无代码写入的 Project Intelligence Runtime。
4. Brain 默认只接收 BrainContextPackageV1。
5. 保存 model、roleVersion、promptVersion、context version 和 Token。
6. 支持流式回复和错误恢复。
7. Brain 可以引用 State、Plan 和 Evidence。
8. Brain 只能生成 Proposal，不能直接写 State。
9. V1 优先使用预构建 Context Package；动态查询工具后置。
10. 新中心增加 Project Brain 面板。

#### 验收

- Brain 对“当前做到哪”回答与服务端事实一致。
- Brain 重新启动或切换模型后不会依赖旧会话记忆维持状态。
- Brain 建议不会自动成为 Decision。
- Brain 没有代码写、Shell 或绕过审批的能力。
- 回答可追溯到 Context Version。

## 第三大周期：智能执行

### 阶段 5：Plan Center 与 Planner Proposal

#### 目标

把目标变成可修改、可审批、可版本化的推进计划。

#### 工作项

1. 建立 Plan / Plan Version / Plan Node Definition / Dependency。
2. 建立独立 Plan Execution State。
3. 建立 `project-planner:v1` Role Contract。
4. 建立 PlanProposalV1 / PlanPatchProposalV1。
5. 建立 base state revision 和 stale 检查。
6. 建立计划 Diff、部分批准、拒绝和发布。
7. 建立节点继承、替换、取消、新增关系。
8. 建立可执行能力校验和 Executor Capability Matrix。
9. 前端使用列表、树和依赖标签。
10. 此阶段仍不自动执行。

#### 验收

- Planner 可以把目标拆成有验收标准和依赖的计划提案。
- 用户批准前不存在正式新 Plan Version。
- 执行进度变化不创建新 Plan Version。
- 基于过期关键 State 的计划不能被无提示发布。
- Replan 可以继承已完成节点。

### 阶段 6：Heartbeat / Lease 与执行可靠性 Gate

#### 目标

在新中心获得执行权限前，避免长期显示虚假的 RUNNING。

#### 工作项

1. 设计 Runtime Heartbeat / Lease 协议。
2. 记录 Run 最后存活时间。
3. 增加 UNKNOWN / LOST 业务语义或等价状态投影。
4. 处理 Node 重启、Provider Run 丢失和迟到事件。
5. 明确 LOST 后 Retry 创建新 Attempt。
6. 新中心显示健康、UNKNOWN、LOST 和恢复入口。
7. 增加超时、重启、竞态和幂等测试。

#### 验收

- Node 崩溃后任务不会无限 RUNNING。
- 暂时网络异常不会过早标记 LOST。
- 迟到事件不会把新 Attempt 的状态覆盖。
- 用户能明确知道旧 Run 是否可恢复。

#### Gate

未通过本阶段，新中心不得成为正式 Work Order 执行入口。

### 阶段 7：Work Order、Execution Bridge 与 Structured Report

#### 目标

跑通第一个完整“计划—执行—证据—状态”闭环。

#### 工作项

1. 建立 WorkOrderV1 和生命周期。
2. 建立 `workOrderId` 幂等认领。
3. 建立 Execution Binding。
4. 通过桥接服务创建 Existing Task/Attempt。
5. 扩展 Runtime Context，使 Worker 接收版本化 Work Order Context。
6. 保持现有 Task/Attempt/Approval/Artifact/Runtime 语义。
7. 建立 ExecutionReportV1 聚合。
8. 分离 Agent Claims、System Evidence、Human Verification。
9. 建立 Verification Gate。
10. 将结果映射到 Plan Execution State。
11. 经 Reducer 生成 Project State Change Proposal 或确定性 Fact。
12. Brain 获得新 Snapshot 并总结下一步。

#### 验收

- 同一 Work Order 重复提交只产生一个 Task 绑定。
- 一个 Plan Node 可以绑定一个或多个历史 Work Order/Task，但关系清晰。
- Agent 说“测试通过”而没有系统证据时，不会成为 SYSTEM_VERIFIED Fact。
- Attempt SUCCEEDED 不会未经验证直接完成 Plan Node。
- 第一个端到端闭环可以重放并追溯。

### 阶段 8：新中心成为主要入口

#### 目标

让新中心覆盖日常项目推进，而旧中心保持 Legacy 状态。

#### 工作项

1. 新中心覆盖 Plan、State、Brain、执行、审批、验收、Artifact。
2. 建立默认入口切换开关。
3. 完成 Archive、筛选、搜索和历史追溯。
4. 完成项目级订阅和断线恢复。
5. 增加性能、Token、错误和健康指标。
6. 完成用户文档和恢复说明。
7. 保留进入技术执行详情的入口。

#### 验收

- 用户只使用新中心可以完成一个长期项目闭环。
- 旧中心是否演进不影响新中心。
- 共享执行内核契约仍有兼容测试。
- 关闭新中心功能开关不会损坏已有 Task 数据。

- 未认证访问新中心业务 API。

- Runtime Token 修改 Decision/Plan。
- Brain/Planner 请求 Shell 或代码写入。

```text
用户建立项目目标
```

同一用例至少连续执行两轮，第二轮从中间故障或 Follow-up 恢复。

# 17. 整体完成标准

新任务中心主线只有满足以下条件才算完成：

## 17.1 产品

- 用户能在一个中心查看目标、状态、计划、执行、证据和待决事项。
- 用户只面对一个 Project Brain。
- AI 建议、正式 Decision 和执行事实视觉上明确区分。
- 用户能理解为什么做、做到哪、证据是什么、下一步是什么。

## 17.2 状态

- Project Identity 不依赖单一路径。
- State 有 Revision、来源、权威等级和证据。
- Brain 重启或模型切换不导致项目失忆。
- 冲突和 stale Proposal 可识别。

## 17.3 计划

- Plan 有不可变版本和审批历史。
- Plan Definition 与执行进度分离。
- Replan 能继承已完成工作。
- Plan Node 不直接等同于 Task。

## 17.4 执行

- Work Order 幂等绑定现有 Task/Attempt。
- Approval、Cancel、Retry、Follow-up 和 Acceptance 继续生效。
- Runtime 失联不会永久伪装运行中。
- 多执行器只使用各自真实支持能力。

## 17.5 证据

- Execution Report 区分 Claim、Evidence 和 Human Verification。
- Plan Node 完成由 Verification Gate 决定。
- 被引用证据不会被普通删除破坏。
- 用户可以从 Decision/State/Plan 追溯到 Attempt/Artifact。

## 17.6 工程

- 新前端不依赖旧 Agent Task Center 业务代码。
- Node 新模块符合仓库模块规范。
- Spring/Node/React 的契约和测试同步。
- 数据迁移可回退到关闭功能，而不是删除历史。
- 关键闭环完成真实 E2E 和两轮稳定演示。

## 18.11 2026-08-15：阶段 2.3 Workspace 移动/重绑定确认与 actor 审计
